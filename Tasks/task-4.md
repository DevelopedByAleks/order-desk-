# Домашнее задание №4 — Order Desk
Роли: CUSTOMER и MANAGER

## 🎯 Цель
Добавить в приложение две роли и ограничить доступ по ним. Всё остальное упрощено: нет регистрации, паролей, восстановления доступа, писем и админки.

**Принцип:** проверки прав пишем явно, в каждом месте отдельно (в странице, в Server Action, в сервисе). Общую абстракцию («матрицу прав») не делаем. После выполнения нужно уметь ответить, где получился дубль и что бы вы из него вынесли.

**Ограничения:** новых зависимостей нет, кроме опционального `@faker-js/faker` для сида. Перед использованием API Next.js читать документацию из `node_modules/next/dist/docs/`. В этой версии много изменений, в том числе вокруг `searchParams` и `cookies`. Нужно уметь объяснить любую строку и каждое решение.

## 1. Пользователи и роли

### 1.1. Модель
Добавить в `prisma/schema.prisma`:
- `enum Role { CUSTOMER MANAGER }`
- `model User` с полями `id`, `name`, `role`
- у `Order` связь с клиентом (`customerId` → `User`)

Затем создать миграцию. Что делать с уже существующими заказами, решаете сами (например, привязать к сид-пользователю или сделать поле nullable). Будьте готовы обосновать выбор.

### 1.2. Сид
Роли создаются только сидом, другого способа создать пользователя нет.
- Файл `prisma/seed.ts`. Подключить его через `prisma.config.ts` (в Prisma 7 seed настраивается там) и добавить скрипт `db:seed` в `package.json`.
- Минимум 3 пользователя вручную: 2 customer и 1 manager.
- Опционально: сгенерировать 15–20 customer'ов через faker, чтобы фильтр по клиенту было на чём проверять.
- Сид идемпотентный: повторный запуск не создаёт дубли и не падает.
- Сид привязывает существующие и/или создаёт новые заказы к customer'ам.

### 1.3. «Вход» (заглушка)
Настоящей аутентификации нет. Вход выглядит так:
- Страница `/login` показывает список пользователей, по клику выбираем «кем быть».
- Выбор кладёт `userId` в cookie (Server Action). Выход удаляет cookie.
- Cookie не подписана, это сознательное упрощение. Будьте готовы рассказать, что здесь не так и как это делают в production.

Файлы:
```
src/app/login/page.tsx           — список пользователей, кнопки «войти как»
src/app/login/actions.ts         — login(userId), logout(): ставят/удаляют cookie, редирект
src/modules/auth/session.ts      — getCurrentUser(): читает cookie, достаёт пользователя из БД, возвращает его или null
src/modules/users/repository.ts  — доступ к данным: findUser, listUsers, listCustomers
```

В `layout.tsx` или в шапке показывать текущего пользователя, его роль и кнопку «Выйти».

## 2. Правила доступа

| | CUSTOMER | MANAGER |
|---|---|---|
| Список заказов | только свои | все |
| Фильтр списка по клиенту | нет | да |
| Страница заказа | только свой | любой |
| Создание заказа | только на себя | на любого customer'а |
| Смена статуса | только отмена `NEW → CANCELLED` | только по цепочке |

- Цепочка для manager: `NEW → PAID → PACKED → SHIPPED → DELIVERED`, только на один шаг вперёд. Что делать с `CANCELLED` и `REFUNDED` для manager, определите сами и зафиксируйте в README в одну строку.
- Редактирование комментария и картинки оставьте как есть. Определите, кому это разрешено, и обоснуйте.
- Незалогиненный пользователь не видит ничего, кроме `/login`.

### 2.1. Защита на трёх уровнях
Каждый уровень проверяется отдельно. UI не считается защитой.

1. **Страница.** Каждая страница сама получает пользователя. Нет пользователя, значит редирект на `/login`. Неподходящая роль, значит редирект или страница «нет доступа» (выберите и обоснуйте).
2. **Server Action.** Каждый action в начале сам получает пользователя и проверяет роль. Нельзя считать, что раз кнопку скрыли, то запрос не придёт. Проверьте руками: вызовите action под чужой ролью и убедитесь, что вернулась ошибка.
3. **Данные.** Customer не должен получить чужой заказ даже по прямому URL `/orders/123`. Фильтрацию делаем в запросе к БД, а не после выборки.

### 2.2. Ошибки доступа
Это учебное задание, поэтому различаем причины отказа явно. Расширить `ErrorKind` в `src/shared/errors.ts`:
- `unauthorized` — пользователь не определён (нет cookie или пользователь не найден);
- `forbidden` — пользователь известен, но действие ему запрещено (чужой заказ, недопустимый переход статуса, действие не для его роли).

Для чужого заказа отвечаем именно `forbidden`, а не `not_found`. Подход «отвечать 404, чтобы не раскрывать существование» тоже валиден и используется в production. Будьте готовы объяснить, чем он лучше и почему мы в этом задании выбрали другой путь.

`normalizeError`, UI и клиентский код (в том числе `error.tsx`) должны понимать новые виды ошибок. Пользователь должен видеть осмысленное сообщение, а не «Что-то пошло не так».

### 2.3. Бизнес-логика переходов
Правила «кто и куда может перевести статус» живут в слое бизнес-логики, а не в action и не в UI.

```
src/modules/orders/transitions.ts  — чистая функция: (роль, текущий статус, новый статус) → допустимо или нет.
                                     Без Prisma, без cookies, без Next.
src/modules/orders/service.ts      — принимает текущего пользователя, зовёт transitions.ts,
                                     бросает AppError("forbidden", …) при нарушении
src/app/orders/actions.ts          — получает пользователя, передаёт его в сервис, ничего не решает сам
```

В `repository.ts` добавить фильтрацию по клиенту (`customerId`) для списка и поиска заказа. Ответственность разделена так: репозиторий умеет фильтровать, сервис решает, когда это нужно.

В UI кнопки и опции статусов показываем только допустимые для роли. Это удобство, а не защита, поэтому сервер всё равно проверяет.

### 2.4. Создание заказа
- Customer создаёт заказ только на себя. В форме нет выбора клиента.
- Manager в форме выбирает клиента из списка customer'ов.
- `customerId` приходит от клиента, поэтому ему нельзя доверять. Сервис сам решает, чей это будет заказ: для customer берёт id из сессии и игнорирует то, что пришло в запросе, для manager проверяет, что такой customer существует. Проверьте руками, что customer не может создать заказ на другого, подменив `customerId` в запросе.

## 3. Фильтр заказов по клиенту (для manager)

Состояние фильтра живёт **только в URL**: `/orders?customerId=3`.

```
src/app/orders/page.tsx                            — серверный компонент: читает searchParams, получает пользователя, ходит за данными
src/modules/orders/schema.ts                       — zod-схема для query-параметров списка
src/modules/orders/components/customer-filter.tsx  — клиентский компонент: селект клиентов, пишет выбор в URL
```

- Страница читает `searchParams` на сервере (в этой версии Next это асинхронное API, проверьте в документации) и перезапрашивает данные при смене фильтра.
- Значение из URL приходит снаружи. Прогоните его через zod-схему. Мусорный `?customerId=abc` не должен ломать страницу.
- Фильтр показывается только manager'у. Что делать, если customer вручную допишет `?customerId=чужой` в URL, решите сами (игнорировать или `forbidden`), обоснуйте и проверьте руками. Решение должно приниматься на сервере.
- Выбор «Все клиенты» убирает параметр из URL.

## 4. Критерии приёмки

- [ ] Миграция и сид работают на чистой БД, повторный сид не ломается.
- [ ] Вход и выход работают, текущая роль видна в шапке.
- [ ] Незалогиненный пользователь попадает на `/login`.
- [ ] Customer видит только свои заказы. Чужой `/orders/:id` отвечает `forbidden`.
- [ ] Manager видит все заказы и может создать заказ на любого customer'а.
- [ ] Customer не может создать заказ на другого, подменив `customerId`.
- [ ] Customer может отменить только `NEW`. Manager двигает статус только на один шаг по цепочке.
- [ ] Прямой вызов Server Action под неподходящей ролью возвращает ошибку.
- [ ] Фильтр по клиенту работает через query-параметры на сервере, невалидные значения не ломают страницу.
- [ ] Правила переходов статусов вынесены в чистую функцию и не зависят от Next и Prisma.
- [ ] `unauthorized` и `forbidden` обрабатываются в общем механизме ошибок и показываются пользователю понятно.
- [ ] `npm run lint` и `npm run build` проходят.
