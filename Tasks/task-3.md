Домашнее задание №3 — Order Desk
Чистая архитектура, одна форма и независимая загрузка файла

🎯 Цель
Функциональность почти не меняется. Главное — чистый код, слои и понимание, что где происходит и зачем.

1. Оставить один вариант формы: состояние в React, файл независим от формы.
2. Разделить код на слои: UI, сеть (Server Actions), бизнес-логика, доступ к данным (Prisma), файловое хранилище.
3. Навести порядок в обработке ошибок — на клиенте и на сервере.

Главный принцип: каждый слой знает только о слое ниже и ничего не знает о слое выше.

Ограничения: стек тот же, новых зависимостей нет. Перед использованием API Next.js читать документацию установленной версии в node_modules/next/dist/docs/. Нужно уметь объяснить любую строку и каждое решение.
1. Форма
Один компонент для создания и редактирования. Он состоит из двух независимых частей:
Часть	Что делает
Загрузка файла	Как только файл выбран — сразу уходит на сервер, состояние загрузки видно в UI
Данные заказа	Статус и комментарий — controlled-инпуты вне <form>. Кнопка «Сохранить» с onClick отправляет данные


1.1. Загрузка файла

1. Пользователь выбирает файл (ровно один).
2. Клиент сразу вызывает Server Action uploadImage(formData).
3. Action сохраняет файл на диск и возвращает fileId (имя, сгенерированное сервером).
4. Клиент хранит состояние в state:

type UploadState =
  | { status: "idle" }
  | { status: "uploading"; fileName: string }
  | { status: "done"; fileId: string; fileName: string }
  | { status: "error"; message: string };

- Пока идёт загрузка, инпут файла и кнопка «Сохранить» заблокированы.
- Блок загрузки — отдельный компонент. Он ничего не знает о заказе, статусе и комментарии, только сообщает наружу своё состояние.


1.2. Сохранение заказа
Кнопка вызывает Server Action с обычным объектом { status, comment, fileId? }. Action не работает с файлами и FormData.

Решить самостоятельно: для создания и редактирования один Server Action или два? Быть готовым обосновать.
1.3. Картинка при редактировании

- Файл не выбран → старая картинка остаётся.
- Выбран новый → заменяет старую.
- Старый файл удаляется с диска только после успешной записи в БД. Если удаление не удалось — ошибка в лог, запрос успешен.
- Удаление картинки без замены не нужно.

1.4. Известное ограничение

Если файл загружен, а заказ не сохранён, файл остаётся на диске. Это сознательное упрощение. Быть готовым рассказать, как решать в production.

2. Архитектура

2.1. Слои
Названия можно менять, разделение ответственности — нет:
app/orders/page.tsx            — контракт Next.js
app/orders/actions.ts          — сетевой слой (Server Actions)
app/orders/_components/        — UI

lib/orders/service.ts          — бизнес-логика
lib/orders/repository.ts       — единственное место с Prisma
lib/orders/schema.ts           — Zod-схема входа (клиент + сервер)
lib/orders/dto.ts              — DTO и маппер

lib/files/storage.ts           — диск
lib/files/image-signature.ts   — проверка сигнатуры (чистые функции)

lib/errors.ts                  — типы ошибок, ActionResult

Слой	Отвечает за	Не должен

page.tsx	Вызвать сервис, преобразовать в DTO, отдать в компонент	Prisma, обработка ошибок БД, разметка списка
UI	Отображение, локальное состояние	Импортировать Prisma, next/server, серверный код
Server Actions	Принять вход, вызвать сервис, вернуть ActionResult, revalidatePath	Бизнес-правила, Prisma
Service	Валидация, проверка fileId, порядок операций, удаление старого файла	FormData, HTTP, React
Repository	Запросы Prisma, перевод ошибок Prisma в ошибки приложения	Валидация, файлы, DTO
Storage	Читать, писать, удалять файлы	Заказы, Prisma


Где бизнес-логика? Подсказка: есть шаги, которые не «сеть», не «БД» и не «диск» — например, «проверить, что присланный fileId реально существует» и «удалить старый файл после успешной записи».

2.2. DTO и Zod-схема — разные вещи

	Zod-схема (schema.ts)	DTO (dto.ts)
Направление	Вход: клиент → сервер	Выход: сервер → UI
Поля	status, comment, fileId	id, status, createdAt, comment, imageUrl
Где используется	Клиент и сервер	Тип — в UI; маппер — только на сервере


- DTO — обычный TS-тип без Zod.
- createdAt — ISO-строка, imageUrl — string | null.
- Prisma → DTO — одна функция в одном месте.
- Отдельные файлы нужны, чтобы клиент не импортировал маппер.

2.3. Проверка архитектуры

- Замена Prisma на другую ORM → меняется только repository.
- Замена диска на облако → меняется только storage.
- Вызов сохранения из Route Handler вместо Server Action → меняется только сетевой слой.
Если приходится править больше одного слоя — слои смешаны.

3. Валидация

3.1. Общая Zod-схема

Одна схема на клиенте и сервере, без серверных импортов. Все правила живут в самой схеме (refine / superRefine), а не в if вокруг неё.
Поле	Правило
status	Значение из enum OrderStatus
comment	Необязательное. После trim: минимум 3 символа, максимум 250 байт. Пустая строка = нет комментария
fileId	Необязательное. Формат как у имён, которые генерирует сервер


3.2. Клиент
- Комментарий проверяется при вводе, ошибка под полем появляется сразу, без запроса.
- «Сохранить» недоступна при ошибках или во время загрузки файла.
- Клиентская валидация — это UX, а не защита.
3.3. Сервер
Проверяет всё самостоятельно:
- Неподдерживаемый статус, комментарий вне границ → validation.
- fileId с неверным форматом или несуществующим файлом → validation. fileId от клиента нельзя подставлять в путь без проверки формата.
3.4. Файл
При загрузке сервер проверяет: файл есть и не пуст, размер ≤ 2 МБ, сигнатура и реальный формат (PNG/JPEG). Нельзя доверять Content-Type, расширению и имени. Имя на диске — UUID + расширение по реальному типу. Файлы лежат в uploads/ (в .gitignore), в БД — только имя.
4. Обработка ошибок
4.1. Типы
Тип	Описание
validation	Данные не прошли валидацию
not_found	Заказ не найден
infrastructure	БД или диск недоступны
unknown	Неожиданная ошибка


- Ошибки Prisma распознаются в одном месте (repository). Остальные слои про Prisma не знают.
- Тексты ошибок БД и stack trace клиенту не уходят, остаются в console.error.
4.2. Контракт
Оба Server Actions возвращают один тип:
type ActionResult<T> =
  | { success: true; data: T }
  | {
      success: false;
      error: {
        kind: "validation" | "not_found" | "infrastructure" | "unknown";
        message: string;
        fieldErrors?: Record<string, string[]>;
      };
    };
Ожидаемые ошибки возвращаются значением, не исключением. Преобразование «ошибка приложения → ActionResult» — в одном месте, а не копия в каждом action.
4.3. Клиент
Показывать понятное сообщение для: ошибки валидации (под полем), ошибки сервера (infrastructure, unknown), отсутствия сети (action бросил исключение), not_found. Ошибки загрузки файла и сохранения заказа показываются независимо.
4.4. error.tsx
Для /orders: понятное сообщение и рабочая кнопка «Повторить». Какие props Next передаёт в error.tsx — найти в документации, не угадывать.
4.5. Лимит Server Actions
Файл больше 1 МБ не должен упираться в стандартный лимит. Найти bodySizeLimit в документации и настроить так, чтобы пользователь видел наше сообщение о размере, а не ошибку Next.js.
