# 1. Архитектура приложения

## 1.1. Разделение на слои (3.1)

Сейчас `page.tsx` одновременно отвечает за:

- Контракт Next.js — маршрутизация и расположение файла.
- Получение данных из БД.
- Рендеринг интерфейса.

**Задача:** разделить эти ответственности.

### Слой 1. `page.tsx`

Страница должна:

1. Вызывать серверную функцию для получения данных.
2. Преобразовывать данные в DTO.
3. Передавать DTO в компонент представления.

В `page.tsx` не должно быть:

- Логики работы с БД.
- Обработки ошибок Prisma.
- Разметки списка заказов.

### Слой 2. Сервисный слой

Серверная функция отвечает за работу с данными.

**Требования:**

- Это единственное место, где используется Prisma.
- Работа с БД вынесена из страницы и компонентов рендеринга.
- Ошибки Prisma распознаются и преобразуются в ошибки приложения.

### Слой 3. `OrderListView`

React-компонент, который получает данные через props и отображает их.

Он не должен импортировать:

- Prisma.
- `next/server`.
- Серверные функции и серверный код.

Компонент не знает, откуда пришли данные.

Внутри `OrderListView` собираются все компоненты, отвечающие за отображение списка заказов.

### DTO — Data Transfer Object

Нужен собственный тип заказа для представления, а не прямая модель Prisma.

Обязательные особенности:

- `createdAt` — строка в ISO-формате.
- `imageUrl` — `string | null`.

**Почему DTO?**

Тип данных должен одинаково выглядеть:

- При передаче с сервера в компонент.
- После сериализации через `JSON.stringify`.
- После получения JSON через `fetch`.

### DTO и Zod

Zod можно использовать для определения схемы данных и получения TypeScript-типа через `z.infer`.

Пример:

```ts
export const orderDtoSchema = z.object({
  id: z.number(),
  status: z.enum(OrderStatus),
  // ...
});

export type OrderDto =
  z.infer<typeof orderDtoSchema>;

export const toOrderDto = (
  o: Order
): OrderDto => ({
  // ...
});
```

Если список будет загружаться через `fetch`, ответ можно проверить:

```ts
const orders = orderDtoSchema
  .array()
  .parse(await res.json());
```

Для `OrderDto` Zod-схема необязательна, но пригодится для проверки ответа API.

### Проверка правильности архитектуры

Представь, что появилась клиентская страница, которая:

1. Выполняет `fetch` к API.
2. Получает заказы.
3. Передаёт их в `OrderListView`.

При правильной архитектуре **`OrderListView` не придётся менять**.

Дополнительно:

- `OrderListView` не должен знать, какой из трёх вариантов формы в нём используется.
- Способ передачи формы в компонент нужно выбрать самостоятельно.

# 3. Три подхода к формам (3.3)

Необходимо реализовать одну и ту же форму тремя способами.

Каждый вариант располагается на отдельной странице.

| Страница | Назначение |
|---|---|
| `/orders` | Индексная страница со ссылками на три варианта |
| `/orders/v1` | Подход 1 — Route Handler |
| `/orders/v2` | Подход 2 — Server Action через `form action` |
| `/orders/v3` | Подход 3 — Server Action как функция |

## 3.1. Подход 1 — Route Handler

Используется запрос к API через Route Handler.

Нужно реализовать:

- Клиентскую валидацию.
- Серверную валидацию.
- Отображение ошибок под полями.
- Обработку ответа API через единый `ActionResult`.

## 3.2. Подход 2 — Server Action + `useActionState`

Используются:

- `<form action={...}>`.
- Server Action.
- `useActionState`.
- `useFormStatus`, где это уместно.

Это единственный подход, где форма отправляет файл картинки на сервер.

## 3.3. Подход 3 — управляемая форма

Используются:

- Поля, хранящиеся в React state.
- Вызов Server Action как обычной функции.
- Клиентская валидация при `change` / `blur`.
- `useTransition`, где это уместно.

### Вопросы для сравнения

Подумай:

- Почему в подходе №3 `useFormStatus` не подходит?
- Почему `useTransition` в подходе №1 не даёт того же эффекта, что в подходе №3?

# 4. Универсальная форма (3.4)

Каждый подход должен поддерживать два режима:

1. Создание заказа.
2. Редактирование существующего заказа.

### Поля формы

- Статус.
- Комментарий.
- Картинка — только в подходе №2.

**При редактировании одна форма должна изменять статус, комментарий и, если применимо, картинку.**

### Правила работы с картинками

**Подходы №1 и №3:**

- Картинка не отправляется.
- При сохранении статуса или комментария существующая картинка должна оставаться.

**Подход №2:**

- Если выбран новый файл — он заменяет старый.
- Старый файл удаляется с диска только после успешной записи изменений в БД.
- Если удаление старого файла не удалось, ошибка записывается в лог, но запрос не считается неуспешным.

Удаление картинки без замены реализовывать не нужно.

# 5. Валидация (3.5)

## 5.1. Общая Zod-схема

Использовать одну схему валидации:

- На клиенте.
- На сервере.

Схема не должна импортировать серверный код.

## 5.2. Клиентская валидация

Ошибки нужно показывать пользователю до отправки запроса.

В подходе №3 это можно сделать на событиях `change` и `blur`.

В подходах №1 и №2 нужно самостоятельно выбрать удобный способ.

### Требования

- Ошибки появляются сразу, не дожидаясь ответа сервера.
- Сообщение отображается под соответствующим полем.
- В README описано, какой подход оказался удобнее и почему.

## 5.3. Серверная валидация

Сервер обязан самостоятельно проверять входные данные.

**Клиентская валидация — это UX, а не защита.**

Даже если клиент отправил невалидные данные напрямую, сервер должен их отклонить.

## 5.4. Проверка изображения

Сервер самостоятельно проверяет:

- Размер файла.
- Сигнатуру файла — первые байты.
- Реальное соответствие допустимому формату.

Недостаточно доверять:

- `Content-Type`.
- Расширению файла.
- Имени файла.

# 6. Обработка ошибок (3.6)

## 6.1. Типы ошибок

Нужно разделять четыре вида ошибок:

| Тип | Описание |
|---|---|
| `validation` | Данные не прошли валидацию |
| `not_found` | Заказ не найден |
| `infrastructure` | Ошибка инфраструктуры, например БД недоступна |
| `unknown` | Неожиданная ошибка |

### Требования

- Ошибки Prisma распознаются в одном месте.
- Ошибки преобразуются в понятные типы приложения.
- На границе приложения — Route Handler или Server Action — ошибки переводятся в нужный формат.
- Тексты ошибок БД и stack trace не отправляются клиенту.
- Внутренние детали остаются в `console.error`.

**Отдельное задание:** найти в документации установленной версии Prisma классы и коды ошибок.

## 6.2. Единый контракт результата

Все три подхода должны использовать один тип:

```ts
type ActionResult<T> =
  | {
      success: true;
      data: T;
    }
  | {
      success: false;
      error: {
        kind:
          | "validation"
          | "not_found"
          | "infrastructure"
          | "unknown";
        message: string;
        fieldErrors?: Record<string, string[]>;
      };
    };
```

### Поведение Server Actions

Подходы №2 и №3 возвращают `ActionResult` напрямую.

### Поведение Route Handler

Подход №1:

- Отправляет тот же объект в JSON.
- Дополнительно передаёт тип ошибки через HTTP-статус.

Клиент во всех подходах работает с одинаковым `ActionResult`.

**Ожидаемые ошибки** (валидация, отсутствие заказа, недоступность БД) возвращаются как значение `success: false`, а не через выбрасывание исключения.

Исключения остаются для неожиданных ошибок.

## 6.3. Ошибки на клиенте

Клиент должен различать:

1. Невалидные данные.
2. Сервер недоступен или сломался.
3. Отсутствует сеть — запрос не дошёл.
4. Ответ пришёл не в JSON.

Для каждой ситуации должно показываться своё понятное сообщение.

## 6.4. `error.tsx`

Добавить `error.tsx` для сегмента `/orders`.

Если список заказов не загрузился, пользователь должен увидеть:

- Понятное сообщение об ошибке.
- Кнопку «Повторить».

Вместо пустой или сломанной страницы.

## 6.5. Лимит Server Actions

По умолчанию лимит тела Server Action — 1 МБ.

Нужно:

1. Найти параметр `bodySizeLimit` в документации установленной версии Next.js.
2. Увеличить лимит.
3. Обеспечить прохождение файла размером более 2 МБ до собственной валидации.
4. Показывать свою ошибку о размере файла, а не ошибку Next.js.

# 7. Хранение картинок (3.7)

## 7.1. Где хранятся файлы

Файлы находятся в папке:

`uploads/`

Папка расположена в корне проекта и добавлена в `.gitignore`.

В БД хранится только **имя файла**, а не содержимое.

## 7.2. Генерация имени файла

Имя создаёт сервер.

Например:

`UUID + расширение, определённое по типу файла`

Имя, присланное пользователем, **никогда нельзя напрямую подставлять в путь**.

## 7.3. Получение изображения

Для выдачи изображения нужен отдельный Route Handler.

Пример:

`GET /api/orders/[id]/image`

Использовать `public/` для загруженных во время работы файлов нельзя: в production они не будут раздаваться таким способом.

В `OrderListView` картинка отображается обычным `<img>`.

Использовать `next/image` не требуется.
