# Домашнее задание №1
## Сквозной скелет Order Desk

### 1. Цель задания

К следующему уроку необходимо разработать работающее приложение **Order Desk**, в котором пользователь может:

- Создавать заказы.
- Просматривать список заказов.
- Изменять статус заказа.
- Сохранять данные в PostgreSQL, чтобы они не пропадали после перезагрузки приложения.

**Главный приоритет — функциональность и архитектура.**

Дизайн пока не требуется. Однако код необходимо сразу писать так, чтобы в дальнейшем можно было легко добавлять интерфейс, новые функции и бизнес-логику.

---

### 2. Технологический стек

| Технология | Назначение |
|---|---|
| Next.js (App Router) | Приложение и серверная логика |
| TypeScript (strict) | Типизация |
| PostgreSQL | База данных |
| Docker Compose | Запуск PostgreSQL |
| Prisma ORM | Работа с базой данных |
| Zod | Валидация данных |

### 3. Что должно работать

**3.1. Запуск проекта**

- Команда `docker compose up -d` поднимает PostgreSQL.
- Приложение запускается согласно инструкции в `README.md`.
- Все команды должны работать на чистой машине после установки необходимых зависимостей.

**3.2. Страница заказов `/orders`**

Страница отображает список заказов со следующими данными:

- `id` — идентификатор заказа.
- `createdAt` — дата создания.
- `status` — текущий статус.

**Сортировка:** новые заказы отображаются сверху.

**3.3. Создание заказа**

Необходимо реализовать форму создания заказа.

На текущем этапе форма содержит только одно поле — начальный статус.

По умолчанию статус `NEW`.

**3.4. Изменение статуса**

У каждого заказа должна быть возможность изменить его статус через:

- Выпадающий список (`select`).
- Кнопку «Сохранить».

Пока разрешены любые переходы между статусами. Ограничения бизнес-логики добавим позднее.

**3.5. Валидация**

- Все входные данные проверяются на сервере.
- Некорректные значения не должны попадать в базу данных.
- При ошибке пользователь должен увидеть соответствующее сообщение.

Например, если вручную подменить значение статуса через DevTools, сервер обязан отклонить такой запрос.

**3.6. Работа с сервером**

Основной вариант реализации — **Server Actions**, без API-роутов.

Список заказов должен отображаться серверным компонентом (Server Component).

---

### 4. Модель данных

Создай одну таблицу `Order`.

Поля:

- `id` — уникальный идентификатор.
- `status` — статус заказа.
- Метаданные заказа (например, дата создания).

**Статусы оформить как enum:**

- `NEW` — новый.
- `PAID` — оплачен.
- `PACKED` — упакован.
- `SHIPPED` — отправлен.
- `DELIVERED` — доставлен.
- `CANCELLED` — отменён.
- `REFUNDED` — возвращены деньги.

### 5. Порядок выполнения

#### Шаг 1. Инициализация проекта

1. Создать пустой Git-репозиторий.
2. Создать проект через `create-next-app`.
3. Использовать TypeScript со строгой типизацией (`strict`) и App Router.
4. Создать отдельную рабочую ветку от `main`.

#### Шаг 2. Docker и PostgreSQL

1. Создать `docker-compose.yml`.
2. Добавить сервис PostgreSQL.
3. Подключить Docker volume для сохранения данных.
4. Добавить строку подключения в `.env`.
5. Создать `.env.example` и закоммитить его в репозиторий.

#### Шаг 3. Prisma

1. Установить и настроить Prisma.
2. Описать модель `Order` в схеме.
3. Создать первую миграцию.
4. Проверить подключение к PostgreSQL.

**Важно:** Prisma регулярно обновляется. Пользуйся документацией именно той версии, которая установлена в проекте.

#### Шаг 4. Prisma Client

Создать общий экземпляр Prisma Client в файле:

`lib/prisma.ts`

Этот экземпляр должен переиспользоваться в приложении.

#### Шаг 5. Серверная логика

Реализовать две операции:

1. Создание заказа.
2. Изменение статуса заказа.

Возможное расположение:

`app/orders/actions.ts`

Каждая операция должна:

- Получать входные данные.
- Валидировать их через Zod.
- Выполнять операцию с БД через Prisma.
- Обрабатывать ошибки.
- Обеспечивать обновление списка заказов после изменения данных.

**Самостоятельное архитектурное решение**

Выбери подход к обработке форм:

- **Вариант A:** Route Handlers + `fetch` (как в стиле Река).
- **Вариант B:** парсинг формы на клиенте и вызов Server Action как функции с типизированными аргументами.
- **Вариант C:** использование `<form action={action}>` с передачей `FormData`.
- **Вариант D:** другой подход, если найдёшь более подходящий.

Решение остаётся за тобой.

На следующем созвоне обсудим:

- Почему выбран именно этот подход.
- Его преимущества и недостатки.
- Чем он отличается от альтернатив.
- Насколько удобно будет развивать такую архитектуру.

#### Шаг 6. Страница заказов

Реализовать `/orders`.

- Получение списка заказов на сервере.
- Отображение данных через Server Component.

- Форму изменения статуса для каждого заказа.

### 8. Вопросы для самопроверки

Эти вопросы разберём на следующем уроке.

**1. Безопасность Server Actions**

Server Action фактически является публичным POST-эндпоинтом.

Почему необходимо проверять данные на сервере, даже если в форме используется `select` с заранее определёнными значениями?

**2. Prisma Client**

Почему не стоит создавать `new PrismaClient()` на каждый запрос?

Что происходит при горячей перезагрузке (Hot Reload) в режиме разработки?

**3. Миграции**

Что делает команда `prisma migrate dev`?

Что хранится в папке `migrations` и почему её нужно коммитить в Git?

**4. Идентификаторы**

Что лучше использовать для `id`:

- Автоинкремент.
- UUID.

Какие преимущества и недостатки есть у каждого подхода?

**5. Обновление данных**

Для чего нужна функция `revalidatePath`?

Что произойдёт, если убрать её после изменения заказа?

**6. Docker и хранение данных**

Что произойдёт с данными PostgreSQL, если пересоздать контейнер без подключённого volume?
